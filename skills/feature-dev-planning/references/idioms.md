# Idioms (stack-agnostic)

The RFC pins the stack; the stack selects which sections below apply. Slice cards reference
these idioms by name so the executor doesn't re-derive them. Principles come first — they apply
to every stack. Per-stack patterns follow.

## Principles (all stacks)

1. **Additive changes first.** New columns, tables, endpoints, and flags are added alongside
   the old path. Nothing existing is deleted until the contract slice. Merges of additive
   changes carry near-zero regression risk.
2. **Explicit over implicit.** Name what a change touches: explicit column lists in SQL,
   explicit parameter objects, explicit return shapes. Never `SELECT *`, never variadic
   option bags that hide required state, never reflection where a literal will do.
3. **One path per behavior.** When extending behavior, prefer adding a new named path
   (function, endpoint, column) over branching inside the existing one. Reviewers see the
   addition; they don't have to re-verify the old path.
4. **Behavior changes are test-covered.** Every slice that changes observable behavior ships
   tests in the same diff. Tests are table-driven where the input space is combinatorial:
   one case per row, edge cases as rows, not as separate test functions.
5. **Migrations never rewrite history.** Forward-only, additive migrations. Data backfills are
   separate slices from schema changes when the backfill is non-trivial.
6. **Design for at-least-once execution.** Anything that can be re-run — backfills, background
   jobs, endpoints under client retry — must be idempotent: running it twice leaves the same
   state as running it once. Guard writes with existence checks or natural keys, not with
   "this will only be called once" hope.

## Go

- Group parameters into a struct when a function grows past ~3 parameters; pass the struct
  explicitly.
- Return `(result, error)`; wrap errors with context (`fmt.Errorf("...: %w", err)`).
- Table-driven tests with `t.Run` subtests; one edge-case row per boundary.

## TypeScript / JavaScript

- Discriminated unions over boolean-flag parameters.
- Explicit types at function boundaries; inference inside.
- Prefer adding a new exported function over an options-object flag on an existing one.

## SQL / Postgres

- Additive `ALTER TABLE ... ADD COLUMN` with a default or `NULL`; never drop or retyped in
  the same migration that adds.
- Backfill with `UPDATE ... WHERE <condition>` in batches for large tables, guarded so
  re-running is safe (`WHERE NOT EXISTS (...)` or an idempotent key). Batch with a keyed
  cursor (`WHERE id > :cursor`), never `OFFSET`.
- New indexes created concurrently (`CREATE INDEX CONCURRENTLY`) when the table is large.

## Python

- `dataclass`/`TypedDict` parameter groups over long positional lists.
- `pytest.mark.parametrize` for table-driven tests.

## Adding a stack

If the RFC pins a stack with no section above, derive the per-stack patterns from the
**Principles** and from the closest analogous code already in the repo. Document the derived
patterns in the RFC's `Design` section so the executor sees them; do not edit this file to
cover every stack.
